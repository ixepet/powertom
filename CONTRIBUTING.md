# Contributing to PowerTom

Thanks for your interest in improving PowerTom. This document covers the setup
and the conventions the project follows.

## Development setup

- Ruby >= 3.3 (required by `ruby_pptx` and `tomlrb`)
- LibreOffice (`soffice`) is needed only for the fidelity tests

```bash
bundle install
bundle exec rspec                        # full suite
bundle exec rubocop                      # style
bundle exec yard doc --no-output         # API docs check
bundle exec bundler-audit check --update # dependency advisories
```

On Windows, `Gemfile.lock` must list the `x64-mingw-ucrt` platform or
`bundle install` fails.

## Windows notes

Windows is a supported development and runtime platform, and it has one
property that shapes the code: **a file with an open handle cannot be
deleted, renamed or overwritten.** See [docs/windows-support.md](docs/windows-support.md)
for the full story.

Two rules follow from it and apply to every change:

- **Any zip entry read must pass a block.** `entry.get_input_stream(&:read)`
  closes the stream immediately; `entry.get_input_stream.read` leaks a file
  handle until the GC finalizer runs. `grep -rn "get_input_stream" --include="*.rb"`
  should never show a call without a block.
- **Do not use `Tempfile.new` for anything whose deletion must be
  deterministic.** Ruby 4.0 defers `File.unlink` to a GC finalizer. Use
  `Tempfile.create` (a plain `File`, no finalizer) and unlink explicitly, or
  keep the data in memory and hand back bytes.

If you have Microsoft Office installed, you can verify rendered decks locally:
see the PowerPoint COM section of `docs/windows-support.md`.

## Test suite

- The unit suite runs everywhere; all examples are expected to pass.
- The **committed mini golden sample** (`spec/fixtures/mini/template.pptx`,
  generated by `tools/build_mini_golden.rb`) exercises split-run merging, page
  cloning/removal, picture replacement, chart binding and LibreOffice fidelity
  in public CI — no private assets needed.
- End-to-end examples that need the larger private golden-sample template
  (`spec/fixtures/hai_mate/template.pptx`) **skip automatically** when the file
  is absent, so a fresh clone always runs a green suite.
- The committed scaffolds (`examples/score_report/*.pptx`) and the public
  fidelity CI job cover the table loops + render + LibreOffice PDF pipeline.
- The **L3 OpenXML validation** workflow (`.github/workflows/l3.yml`) checks the
  rendered deck set with Microsoft's `OpenXmlValidator` on a Windows runner and
  is a hard gate. Locally you need the .NET SDK; run the tool with
  `dotnet run --project tools/openxml_validator -c Release -- <deck.pptx>`.
- If you have the original golden template, regenerate its snapshot with:

  ```bash
  bundle exec rake fixtures:generate TEMPLATE=/path/to/template.pptx OUT=spec/fixtures/hai_mate
  bundle exec rake fixtures:check OUT=spec/fixtures/hai_mate
  ```

## Conventions

- **User-facing messages are English.** Errors, warnings and `PowerTom.check`
  reports must be in English; code comments may be either language, but new
  comments are preferably English too.
- Every error message carries location information (slide number, shape name,
  tag). Keep that property when adding new checks.
- Failing loudly beats silent fallbacks: missing fields and structural mistakes
  raise or produce errors, never blank output.
- Add or update tests for any behaviour change; table syntax changes need
  structural-invariant tests (row `tc` count == `tblGrid` column count).
- Add a `CHANGELOG.md` entry under the unreleased/next version.

## Pull requests

1. Fork and create a feature branch.
2. Make the change with tests.
3. Run the full suite, RuboCop and YARD locally.
4. Open the PR with a short description of the behaviour change and the reasoning.

Bug reports and feature requests: use the issue templates. For security
issues, please do not open a public issue — see the Security section of the
README and open a private security advisory instead.

## Releasing (maintainers)

Releases are published by pushing a `v*` tag; `.github/workflows/release.yml`
runs `rubygems/release-gem`, which publishes the gem via RubyGems trusted
publishing (OIDC) and signs it with Sigstore — RubyGems then shows the build's
provenance. No manual `gem push` or OTP.
